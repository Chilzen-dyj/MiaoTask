# 贡献规范

欢迎修复问题、补充机型和活动适配，或完善使用体验。提交前阅读 [README](../README.md) 与[开发文档](DEVELOPMENT.md)，确认现有入口和模块职责。较大的结构调整请先在 Issue 中说明目标、兼容方式与迁移范围。

## 修改边界

* 一个 PR 聚焦一个问题，避免夹带无关重构、依赖升级或批量格式调整。
* 保持现有配置字段、默认值、CLI 和每日记录的兼容性；确需改变时说明影响并提供迁移或回退方法。
* 遵循 [架构与扩展](ARCHITECTURE.md) 的依赖方向，任务执行、识别、设备驱动、状态记录和界面分别维护，不把手机坐标或活动判断塞进前端。
* 操作与恢复必须有次数、超时及停止边界；任务成功需要页面反馈，不能仅按停留时间推断。
* 分身操作必须保留用户空间限制与前台身份核对；应用缺失根据当前设备的实际反馈判断，不预设别人的安装情况。
* 不安装或替换系统输入法，不自动处理安全认证、支付、下单、拉人或助力。
* UI 优先保留直接开始的简单路径，高级选项按需展开；文案描述用户行为，避免暴露无关实现细节。

项目结构可能继续调整。新能力先在现有职责内实现；跨模块重构另行说明，不按尚未确定的后续架构预先搬动代码。

## 验证与 PR

验证命令及便携包检查集中在[测试与打包](BUILDING.md)。PR 请说明：

1. 解决的问题、复现条件、主要改动和影响范围。
2. 执行了哪些检查及结果；配置、旧数据、停止和恢复路径是否保持兼容。
3. 改动过的任务或配置分支提供相应回归用例；保留已有用例，不删除检查来换取通过。
4. 真机验证注明机型、系统、应用版本及覆盖路径；未覆盖的情况如实列出。纯文档或展示修改无需添加照抄实现的测试。

采用模拟设备和构造数据编写用例，不把真实账户或手机记录作为固定样例。任务适配问题可附脱敏截图；完整诊断包可能有个人信息，先按[风险与隐私](SAFETY.md)检查。

## 文档与提交

* README 只保留项目介绍、下载入口、功能与文档索引；细节放入对应 docs 文件。
* 使用方式变更更新 `USAGE.md`，结构变更更新 `DEVELOPMENT.md`；用户可见变化合并到 `RELEASES.md`，不为每个版本、会话或测试轮次新增说明文件。
* 测试命令、构建要求和验证方法只在 `BUILDING.md` 维护，不在用户说明重复测试通过数量。
* Release 说明使用一句概括及「【新增】」「【优化】」「【修复】」条目，具体写法与同版本替换流程见 `BUILDING.md`。
* 提交前检查暂存区，排除设备标识、日志、截图、私钥、本地配置、虚拟环境和构建产物。
* 保留上游来源与第三方许可。不要擅自赋予上游代码新的许可证。
* PR 标题和描述写清最终行为；发布、打标签、覆盖附件或删除 Release 由维护者统一安排。

## 使用 AI 辅助开发

让 AI 先阅读本规范、开发文档和相关代码，再修改实现；不要只根据截图猜测状态或硬编码某一台手机。提供问题、约束和预期行为，不提供登录凭据、调试私钥或未经脱敏的设备记录。

检查生成代码的错误处理、配置兼容、实例边界与停止行为。提交说明中列出实际执行的验证和仍有疑问的部分，不把静态推断、模拟结果或剪辑画面描述为真机成功。AI 不应自动推送、发布或调整 Release。
