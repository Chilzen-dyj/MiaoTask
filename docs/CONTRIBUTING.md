# 贡献规范

开始修改前按顺序阅读 [ARCHITECTURE](ARCHITECTURE.md)、本规范和 [DEVELOPMENT](DEVELOPMENT.md)。先确认依赖方向和契约，再定位代码；验证与打包命令统一在 [BUILDING](BUILDING.md)。较大的结构调整请先在 Issue 说明目标、兼容方式与迁移范围。

## 职责选择

| 改动 | 所在位置 | 不应承担的职责 |
| --- | --- | --- |
| 设备连接、模拟器、屏幕与坐标 | `backend/core/device/` | 活动文案、任务奖励或平台包名判断 |
| 调度、停止、返回预算和日志上下文 | `backend/core/execution/`、`core/context.py` | 网页控件或全局“当前设备” |
| 设备工作区与 HTTP | `backend/core/service/` | 具体活动的点击规则 |
| 应用与活动适配 | `backend/app/<app>/` | 绕开设备接口、直接调用 ADB 或读取其他设备的记录 |
| 页面与交互 | `frontend/` | 保存配对码、判断任务成功或推断坐标 |

新增应用从 manifest、配置、入口、任务解析、执行与核验开始，复用设备和会话契约。不要复制一份控制台或 HTTP 服务来适配新平台，也不要在 core 中增加平台名称分支。

## 修改边界

* 一个 PR 聚焦一个问题，避免夹带无关重构、依赖升级或批量格式调整。
* 保持现有配置字段、默认值、CLI 和每日记录的兼容性；确需改变时说明影响并提供迁移或回退方法。
* 遵循 [架构与扩展](ARCHITECTURE.md) 的依赖方向，任务执行、识别、设备驱动、状态记录和界面分别维护，不把手机坐标或活动判断塞进前端。
* 操作与恢复必须有次数、超时及停止边界；任务成功需要页面反馈，不能仅按停留时间推断。
* 每台设备有独立控制器、工作线程、停止句柄、读屏器和统计。用户在网页切换标签只改变当前展示，不应改变其他工作线程的目标；请求携带明确工作区 ID，失效 ID 必须拒绝，不能回退操作另一台设备。
* 同一物理设备的 USB、Wi-Fi、mDNS 或模拟器别名共用独占连接租约。取得租约后才能初始化自动化驱动；运行中不得更换连接、活动或应用实例。批量启动将任务交给各设备线程，不逐台等待完成。
* 截图、UI 树与输入使用同一个 Android 显示屏。逻辑屏幕 ID、物理采集 ID 和列表序号不能混用；映射失败时停止，不能偷偷改用主屏。旋转后重新读取尺寸，OCR 裁剪与缩放必须回映到原始设备坐标。
* 使用系统报告的安全边距和挖孔区域约束操作；不要硬编码某一机型的分辨率、密度、端口或弹窗位置。找不到控件时保留现场并有限恢复。
* 并行设备不能共享可变的 OCR 推理状态或日志上下文；预览只读取选中设备需要的画面，不为所有后台设备持续截图。
* 分身操作必须保留用户空间限制与前台身份核对；应用缺失根据当前设备的实际反馈判断，不预设别人的安装情况。
* 不安装或替换系统输入法，不自动处理安全认证、支付、下单、拉人或助力。
* UI 优先保留直接开始的简单路径，高级选项按需展开；文案描述用户行为，避免暴露无关实现细节。

项目结构可能继续调整。新能力先在现有职责内实现；契约变化应同步说明迁移与调用者影响。

## 验证与 PR

验证命令及便携包检查集中在[测试与打包](BUILDING.md)。PR 请说明：

1. 解决的问题、复现条件、主要改动和影响范围。
2. 执行了哪些检查及结果；配置、旧数据、停止和恢复路径是否保持兼容。
3. 改动过的任务或配置分支提供相应回归用例；保留已有用例，不删除检查来换取通过。
4. 真机验证注明机型、系统、应用版本及覆盖路径；未覆盖的情况如实列出。纯文档或展示修改无需添加照抄实现的测试。
5. 涉及设备管理时，验证并行运行、单台暂停与停止、重复物理设备、失效工作区、批量部分失败、移除与全局退出。涉及识别时，覆盖横竖屏、比例变化、坐标回映与系统区域；登录、认证和不可读取画面必须保留停止边界。

采用模拟设备和构造数据编写用例，不把真实账户或手机记录作为固定样例。任务适配问题可附脱敏截图；完整诊断包可能有个人信息，先按[风险与隐私](SAFETY.md)检查。

## 文档与提交

* README 只保留项目介绍、下载入口、功能与文档索引；细节放入对应 docs 文件。
* 使用方式变更更新 `USAGE.md`，结构变更更新 `DEVELOPMENT.md`；用户可见变化合并到 `RELEASES.md`，不为每个版本、会话或测试轮次新增说明文件。
* 测试命令、构建要求和验证方法只在 `BUILDING.md` 维护，不在用户说明重复测试通过数量。
* Release 说明使用一句概括及「【新增】」「【优化】」「【修复】」条目，具体写法与同版本替换流程见 `BUILDING.md`。
* 提交前检查暂存区，排除设备标识、日志、截图、私钥、本地配置、虚拟环境和构建产物。
* 保留上游来源与第三方许可。不要擅自赋予上游代码新的许可证。
* PR 标题和描述写清最终行为；发布、打标签、覆盖附件或删除 Release 由维护者统一安排。

## 使用 AI 辅助开发

让 AI 先读根目录 `AGENTS.md`，再按其中顺序阅读架构、规范、开发文档和相关实现。要求它先明确改动归属、已有契约和兼容影响，再修改代码；不要只根据截图猜测状态或硬编码某一台手机。提供问题、约束和预期行为，不提供登录凭据、调试私钥或未经脱敏的设备记录。

检查生成代码的错误处理、配置兼容、实例边界与停止行为。提交说明中列出实际执行的验证和仍有疑问的部分，不把静态推断、模拟结果或剪辑画面描述为真机成功。AI 不应自动推送、发布或调整 Release。

提交前逐项核对：

* [ ] 职责和依赖符合架构，未新增隐式全局设备、跨平台耦合或重复服务。
* [ ] 旧配置、接口和日记录保持兼容；必要的迁移与回退已有说明。
* [ ] 相关回归通过，设备及页面实测结果与未覆盖范围已写入 PR。
* [ ] 使用、架构和统一发布记录按影响更新，未复制新的版本说明文件。
* [ ] 暂存区不含实际设备地址、账号、配对码、截图、环境和构建产物。
